# R265：大对象DROP在路径分配失败后遗留临时文件

状态：临时名创建后的C++分配窗口已消除，并完成有限验证；STO-07/WAL-07与原273总清单仍未整体完成。

## 缺陷与修改方法

| 缺陷 | 影响 | 修改方法 |
| --- | --- | --- |
| mkstemp创建空reservation、关闭fd后，再构造filesystem::path backup | 字符串或路径组件分配抛bad_alloc时，DROP尚未处理原对象，却遗留隐藏.lo_drop_*文件；既有fd自动释放无法清理这个名字 | 在创建文件前准备可写std::string backup，直接mkstemp(backup.data())，后续复用c_str()，不再重建路径 |

生产只改LargeObject.cpp的这一段临时名准备代码。使用既有C++17字符串可写缓冲区，
mkstemp仍只修改末尾模板字符；没有改临时名格式、原对象内容、名字身份校验、rename/
link/unlink、目录同步或失败回退顺序。其他函数和R264的fd拥有者保持原样，无新公共
头、API、类布局、文件格式、Main、WAL、CLOG或全局registry改动。

## 完整旧新对照

同一夹具在Root与纯提交投影各完整324控制：旧实现两侧各162失败、退出1，实际注入
162次bad_alloc并观察到162个空隐藏文件；新实现两侧各324通过、零失败、退出0，
没有CONTROL_ERROR。原对象在这些旧失败中没有丢失，问题是残留名字，不夸大为数据丢失。

| 控制族 | 数量 | 覆盖 |
| --- | --- | --- |
| 2对象长度 ×2路径布局 ×9模式的正常分配点发现 | 36 | 257/4099字节，短路径/含150字符组件的长路径；本机短路径4个、长路径5个创建后分配点，共162个 |
| 每配置固定8个故障序号 | 288 | 遍历全部观察点及超过末端的健康控制；异常不得遗留隐藏名字或改变原对象，正常返回须符合该I/O模式 |

9种模式为正常、首次目录同步失败、对象已不存在、对象位置为非空目录、reservation
close错误、源open错误、rename错误、源close错误及最后清理目录同步失败。原有返回值、
原对象/目录内容、相关fd数量、健康及幂等DROP重试、新manager读取均校验。

新实现的36个正常配置实测创建后分配点全部为0：旧162个可失败位置已被消除，因此
相同固定故障序号在新实现中不再触发分配异常。报告新INJECTED=0，不把没有发生的
bad_alloc伪称为已注入；未删除任何控制或放宽资源/数据期望。

夹具按私有路径识别真实mkstemp/mkstemp64成功后才开始计数，覆盖new/new[]及
aligned/nothrow系列，且只作用于测试线程。实际内存分配与正向POSIX调用仍转发真实
实现；覆盖open/open64及强化入口，close EIO在实际关闭后注入，rename EIO在改名字
前返回。目录同步使用既有测试注入点。不耗尽系统RAM，不声称自然内核或硬件故障。

旧失败先记录隐藏文件，再核对device/inode、普通文件和零长度，随后仅由夹具删除
自身reservation以继续测试，不把手工清理算作产品自动恢复。对象缺失/目录占位也是
私有夹具预置状态，观察返回后才恢复或用公开API重建以验证健康重试。只清理自身
mkdtemp目录；新正常执行没有隐藏文件或对象fd残留。
