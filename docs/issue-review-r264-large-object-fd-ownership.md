# R264：大对象异常路径的文件描述符泄漏

状态：四条普通大对象API路径的对象fd所有权已修复并完成有限验证；不是全部异常路径或STO-07整体验收。

## 缺陷与修改方法

| 缺陷 | 影响 | 修改方法 |
| --- | --- | --- |
| read打开对象后，缓冲区resize抛bad_alloc时跳过手工close | 每次失败遗留对象fd；连续32次失败实际留下32个 | 打开后立即交给局部拥有者，普通返回及异常展开均自动关闭 |
| 构造时已打开对象，sizes_节点分配失败 | manager构造失败，却遗留用于加载对象大小的fd | 为每次扫描取得的对象fd建立相同局部所有权 |
| create遇peer已创建的ID，登记其大小时节点分配失败 | CREATE调用抛异常后遗留已有对象fd | 对EEXIST分支的已打开对象fd建立局部所有权，不改原对象或ID语义 |
| export已打开源对象，输出流初始化分配失败 | 导出抛异常后遗留源fd | 源fd建立局部所有权；正常结束仍显式检查close结果，关闭后清空所有权以免重复关闭 |

生产只改LargeObject.cpp：新增匿名namespace内不可复制、无动态分配的OwnedObjectFd，
使用于上述4个拥有原生fd的位置。析构不抛异常，显式close先撤销所有权再调用POSIX
close；不会因close报错再次关闭同一数字fd。没有将借用fd转移为自有资源。

原bad_alloc仍向调用者传播，不转成成功，不增加catch吞掉异常。导出的正常close错误
仍使bool结果为false；其他原本忽略close错误的路径没有新增错误返回策略。write、
truncate、drop、import、size及openRegularObject函数体不改，R262/R263的数据语义保留。
没有新公共头、API、类布局、文件格式、Main、WAL、CLOG或全局registry改动。

分配点大小为read的N+1、两种轻量索引节点48字节、输出流缓冲8192字节，是本机实际
观察，不是其他标准库的固定承诺。夹具只在自己的对象路径打开且fd身份匹配时监控
new/new[]及aligned/nothrow系列，按所观察序号抛bad_alloc；不耗尽系统内存，不把
确定性注入称为自然OOM。正向内存分配仍使用真实分配器。

open/open64及强化入口__open_2/__open64_2均转发真实libc；close错误是实际关闭后
注入，不能推断其他平台在close失败后仍持有fd的行为。检查目标对象fd数量、源对象
字节不变、健康重试和新manager可读；CREATE不会覆盖peer内容。旧实现泄漏先被记录，
再由夹具仅关闭其自身见证的私有fd，手工清理不算产品自动恢复。

准备期V1只拦截open而实际构建使用__open_2，15项均为未命中的CONTROL_ERROR，不能
算产品失败。原V1源码/日志保留，nm确认符号后补足入口，生产编译选项未弱化。V2
已完整观察旧两侧51/27失败、新两侧51/0及sanitizer 51/0，日志不覆盖。V3仅将注入
限制到测试线程：其他线程在读取共享故障状态前即转发真实操作，不改变任何控制和
断言；V3再次完整旧新及sanitizer验证，旧新12条分配点/大小完全一致。整合脚本另有一次把class声明计作变量的断言错误，在修改生产
文件前停止，修正为精确四个变量检查后才整合；未把脚本失败计作数据库缺陷。
