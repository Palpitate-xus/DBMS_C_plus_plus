# R286：TRANSLATE 重复扫描与逐字符临时对象

状态：有限性能修复；不是旧版错值修复，不关闭整个 FUNC-01 或原 273 条总清单。
刚按用户要求暂缓的 [R285 页分配失败原子性](issue-review-r285-allocation-failure-deferred.md)
不恢复，其生产实现保持原样。

## 问题和修改方法

| 问题 | 影响 | 修改方法 |
|---|---|---|
| 每个输入字符都从头线性查找 FROM 字符表 | n 个字符配 m 个映射，最坏需要 n×m 次字符比较 | 一次建立字符哈希表，逐字符查找；为平均复杂度改善，不承诺哈希最坏情况严格线性 |
| 把整个输入、FROM 和 TO 都拆成拥有内存的字符串数组 | 输入字符数较多时产生与字符数相称的额外对象存储 | 在不可变局部字符串上使用 string_view，按原 UTF-8 边界流式遍历；映射仅保留不同 FROM 字符的视图 |

视图的拥有者始终是同次调用中的三个局部字符串，不跨行或跨调用缓存。
保留重复 FROM 字符的首次映射；重复项仍消耗相应的 TO 位置，多余 FROM 字符
表示删除，多余 TO 字符忽略。映射不递归作用于新输出，按码点而非字素簇处理。
空输入/空 FROM 可直接返回，但不改变实参的既有求值次数或严格 NULL 规则。
CHAR 去尾填充、VARCHAR/TEXT、函数身份与 native override 保持原行为。

只改实际 TRANSLATE 回调及 CPP 自身的两个标准库 include；无公共头、布局、
磁盘格式、签名、排序规则、全局载体或字符串上限变化。不扩大 UTF-8 输入准入范围。
仍需要原三个文本副本、输出和不同映射数量对应的哈希表，不是常量内存声明。
语义依据为 [PostgreSQL 18 字符串函数](https://www.postgresql.org/docs/18/functions-string.html)，
并用本机实际 PostgreSQL 18.6 对同一协议夹具完整对照。

## 固定旧新对照

| 范围 | 旧版 Root / 纯提交 | 修复后 Root / 纯提交 |
|---|---|---|
| 新原生完整 120 控制 | 各 exit 0、零失败 | 各 exit 0、零失败 |
| 新协议完整 402 控制 | 各 exit 0、零失败 | 各 exit 0、零失败 |
| 实际 PostgreSQL 180006，同一协议 402 控制 | exit 0、零失败 | 独立参考，不是修改后产品生成的期望 |

32 组固定文本涵盖重复映射/删除、映射位置消耗、首尾与未命中、ASCII/多字节/
emoji/组合码点、空串、额外 TO、引号、反斜线和换行。原生同时验证 typed
TEXT/VARCHAR 与 SQL、6 个 CHAR 控制、7 种 NULL 掩码、纯类型推断、每个实参
单次求值及自定义同名回调。大映射测试分别使用 1024/4096/8192 个不同字符，
输入各 65,536 个末项命中或不命中字符，始终比较完整输出。
协议覆盖 Simple/Extended、文本/二进制输入输出、引用/限定名称、参数描述、
实际表行、空结果、LIMIT 0 和 sequence 副作用计数。

初次协议夹具机械改名误改了三个 Python `str.replace` 方法，Root 在第一条
业务 SQL 发送前因 TypeError 退出 1；它不是产品失败，也没有完整通过 footer。
仅恢复这三个 Python 方法，所有 SQL、期望、案例和 deadline 不变；旧夹具和
失败日志保留。之后最终 V2 同 SHA 在旧版两侧、PG 和修复后两侧完整执行。
没有删失败断言、放宽超时或把性能旧问题记作 120/402 个错值缺陷。
