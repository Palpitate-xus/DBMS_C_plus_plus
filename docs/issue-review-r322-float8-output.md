# R322：FLOAT8 文本显示与 PG18 不一致

状态：DEFERRED（2026-10-29，按用户最新“skip it”要求暂缓）；候选实现未验收、未提交生产代码。

## 复现与影响

```sql
SELECT CAST(16777217 AS double precision) AS v;
SELECT CAST('1e23' AS double precision) AS v;
CREATE TABLE r322_stored(id integer,v double precision);
INSERT INTO r322_stored VALUES(1,CAST('16777217' AS double precision));
SELECT v FROM r322_stored;
```

PG18.6 返回 `16777217`，旧产品返回 `1.6777217e+07`；直接存储读取也复现。
`1e23` 旧产品输出 `1e+23`，PG18.6 输出 `9.999999999999999e+22`。
已检查的二进制值相同，这是文本表示规则，不是重新计算数值或精度丢失。
客户端显示、CAST AS TEXT、已有 DOUBLE 标量函数及存储列读取均受影响。

## 原因与修改方法

std::to_chars 的通用格式显示阈值不等于 PG 的 FLOAT8 输出阈值：PG 对
十进制指数 -4 至 14 使用定点表示。此外 PG 默认拒绝恰处于两个二进制
数舍入中点的最短十进制表示；只改阈值无法修正正负 `1e23`。

增加私有共享输出实现：以现有最短往返候选为起点，用整数的奇数尾数和
二进制指数精确检测中点；必要时逐精度选择真正往返且不在边界的候选，
再按 PG 阈值显示。无浮点中点运算、无大整数依赖、无 NUMERIC 模块改动。
保留负零、NaN、正负无穷；不改变原有数值运算和物理存储位。

仅接入 ExprEvaluator 的 DOUBLE 输出与 TableManage 中实际 DOUBLE 列的
显示读取。原 formatFloatingValue 同时用于内部索引键、几何、REAL、
旧定长 decimal/numeric，因此不得整体替换；这些旧路径保持字节不变。
FLOAT4 原函数体保持；不恢复用户暂缓的 REAL 扩宽/算术、通用规划、
物理身份、窗口或其他模块，不改 Main、Parser 或公共头。

## V1 失败保留与 V2 的 DOUBLE ABS 交接（尚未验收）

V1 两侧真实 evaluator 的 35,968 检查均成功，但完整 436 SQL 各仍有
112 严格差异：108 处来源 OID，另有 75/79/130/134 四处 ABS 数据差异。
这些不是新增回归：旧已验收 R321 的对应差异也存在。原 V1 源码、
对象、二进制、原生成功和协议失败日志均保留，没有验收或提交 V1。

原因是旧 applyScalarFunc 的 ABS 分支把结果先用 double 计算，再将
整数值转 int64 输出；大值/非有限值可能返回错误值，而不仅仅是显示风格。
通用 strictFns 预检查和后续函数分支会分别求参。实际三次
ABS(CAST(nextval(...) AS DOUBLE)) 返回 2/4/6，PG 为 1/2/3，最终计数
6 对 3，均在 V2 生产修改前观察。不能为了本项通过而删除这些请求。

扩展为 489：PG 全成功，原 436 请求及期望帧精确前缀保留；旧已验收
R321 两侧各 184 严格/104 排除私有 OID 后的数据差异，V1 各 143/35。
增加大值、正负无穷、NaN、负次正规、typed NULL、参数一次求值控制。
来源差异中只有四个 relation OID 字节另行比较，列序号、类型、长度、
typmod、格式、零来源是否存在均严格保留，并检查实际 OID 映射一一对应。

V2 只对实际 AST/列声明为 DOUBLE 的 ABS 参数，交给已有 typed evaluator
执行调用本体，但其前方的通用预检查仍会先 getVal，故尚未消除重复。REAL、NUMERIC、
未知类型的旧 ABS 分支保持原字节，不改通用 CAST/getVal、Main、Parser、
公共头或其他暂缓模块。此处补全 DOUBLE 输出所需的正确值交接，不仅
是文本格式；不声称所有其他 CAST 路径都已解决重复求值。
尚须完整 489、原 168/747、原生、回归及 scoped UBSan 后才能本地提交。
