# R284：存储对象打开失败后的清理和同对象重试

状态：修复 PageAllocator / BufferPool 的异常打开状态；不代表完整资源治理、
存储、事务、WAL 或原 273 项总清单已完成。生产只修改两个 CPP，不改头、ABI 或磁盘格式。

## 缺陷与修改方法

| 缺陷 | 实际影响 | 修改方法 |
|---|---|---|
| PageAllocator 的异常保护只覆盖空闲链，页头 pin 的 guard 建立过晚 | `bp.open()`、页头读取或文件头验证中的异常可留下打开的池、fd 或 pin；下一次 `open()` 提前返回 true，实际 `numPages` 尚为 0 | 从缓冲池打开开始建立完整异常边界；取得页头后立即拥有 pin；异常时先展开局部 guard，再关闭池且禁止写回，复位未发布的成员状态并重抛原异常 |
| BufferPool 在打开主文件后构造辅助文件名，缺少异常回收 | 字符串分配失败后主 fd 仍打开，对象却没有完成初始化；直接调用 BufferPool 也会受影响 | 在 `openInternal()` 中回收实际拥有的两个 fd、复位描述符并重抛；普通返回 false 的策略和辅助文件策略保持不变 |
| 关闭后重建帧数组时，仅用数组长度判断准备就绪 | 中途分配失败后数组仍有配置长度，但部分 `Frame.data` 为空；同对象重试跳过重建，真实页读取出现 SIGSEGV | 打开异常路径清除不完整帧和映射、复位 clock，使重试重新建立全部帧 |

这是实际存储 API 故障注入，不是手工模拟错误状态，也没有证明某个既有 SQL
请求触发同一 OOM 调度。未修改全局缓存、密码算法、权限、原子文件模块或后台清理。
旧版实际观察到了半打开对象、存活目标 fd、未释放页头 pin 和重试崩溃。

340 是重复场景的失败案例数，不是 340 个不同 bug。两侧旧程序 exit 1、新程序
exit 0，使用完全相同的最终 V5 测试源码。没有减少旧失败案例，也没有把新的
实现替换成测试模型。1074 来自每条正常路径的真实调用 trace，不是构造的空故障。

PageAllocator 的 8 种输入各测试初次打开/同对象关闭后重开：不存在、已有空文件、
仅头页、活页、1/19 个空闲页、legacy v4 活页/空闲页和当前 v5。BufferPool 的
`open()` / `openExisting()` 各测试两种已有文件与两种生命周期，共 24 条正控路径。
构造和文件名 registry 预热在注入窗口外；没有声称覆盖所有全局首次初始化。

每条路径记录 `open()` 内实际 C++ `new` 的大小、fd/读取阶段和页号，逐点真实
注入一次 bad_alloc，包含普通、数组、nothrow 和 aligned 重载的观察入口。
filesystem 的 error_code 重载允许内部恢复为完整成功或正常 false；失败必须
关闭干净，成功必须完整可用。另有 104 个真实 heap `pread` 故障，覆盖页头、
空闲链头/尾的 EIO、runtime_error、`DbError(58030)` 和非 std 异常；检查原值与类型。

失败后先观察关闭状态、页数、fd、pin、完整文件字节和零写回，再直接使用同一
对象重试，不先调用 close 来掩盖旧状态。重试读取原行、耗尽空闲页、验证唯一
页号并扩展超过全部 16 个帧；写入不同的 64 字节载荷，flush/close/open 后逐值
验证。直接 BufferPool 也填满所有帧，包括 EOF 零页，避免漏过后段空帧。
保留既有 O_CREAT 行为：失败的新建打开可留下零字节文件，不把这等同原子创建
或承诺删除它；已有文件的完整字节必须保持不变。

## 夹具修正与保留的失败

| 阶段 | 实际结果与处理 |
|---|---|
| V1 | Root 在 legacy v4 正控退出 120：夹具错误使用仅适用于绑定 v5 页的 `isValid(id)`。改为 v4 结构/checksum 检查，v5 继续校验物理页号；旧源码、部分原始失败和 receipt 保留，不计完整基线 |
| V2 | Root 在原 180 秒上限退出 124；driver 还因失败 receipt 与 V1 同名而 assert，原记录没有被覆盖。保存精确终端响应与原日志；纯提交侧未运行 |
| V3 | 保留全部被测局部对象析构并加 fd 检查，随后仅跳过 exec worker 无关的全局测试引擎收尾；仍在 180 秒退出 124，不计通过 |
| V4 | 增加独立 worker 最多 4 并发、CLOEXEC pipe、exec 前已解析的 close 和日志分组；自包含设置受支持的 16 帧测试配置。仍退出 124；原案例/断言和期限保持 |
| V5 | 实际发现系统 core_pattern 会为每次 SIGSEGV 启动 apport，即使 core limit 为 0。只在测试 worker 中记录 SIGSEGV/SIGBUS 后以失败码退出，避免系统报告器；区分 observed_signal 与原始 wait_signal，不把信号改成通过。完整旧对照及新验收均使用此版 |

未改系统配置。致命信号 handler 不恢复执行、不跳过故障案例；正常 worker
只有在 `child()` 的所有被测局部对象已经析构且 fd 再检查后才 `_exit`，不宣称
全局引擎析构、后台清理或 LSan 已验证。exec 前只做 fd/chdir/exec 等操作，
各 worker 私有 cwd，故障只对调用线程生效。原生 180 秒和 worker 5 秒期限均未提高。
前几轮没有完整 footer，不能与 V5 拼接为完整运行或写成已通过。
