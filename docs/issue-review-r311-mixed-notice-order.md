## 问题、复现与方法

纯接受副本先追加本次结构化通知，再扫描 stdout 的旧式通知，导致不同来源
的通知不按发出顺序抵达客户端。Root 隔离投影已有未接受的另一套结构化
接收器，先收集该通道、再追加新通道，也有相同的跨通道顺序问题。

使用真实网络服务器、Simple 与 Parse/Bind/Execute/Sync、测试执行回调复现；
不使用 DO 或存储例程来绕过用户暂缓范围。12 种通知排列/成功与错误场景，
5 个连接（含 4 个并发连接），每次再发送无通知请求检查串消息，共 240 项。
断言检查顺序、严重级别、SQLSTATE、正文、严格帧、空 Parse/Bind 完成帧与
ReadyForQuery；同正文异状态用例确保不能按文字匹配状态。

初版回调对两侧都写 stdout，纯副本 80 项失败、Root 110 项失败。源码核对
确认 Root 已不把 stdout 当诊断，故不能把其 110 项全算产品缺陷。保留初版
源码及日志，只让回调按各侧实际支持的旧生产接口发出旧通知；240 项 SQL、
预期、正文与帧全部不变。重新编译并在原 R308 生产对象上运行，两侧各 80
项失败，失败排列并不完全相同，不能仅凭计数断言相同失败身份。

修复把结构化通知的位置绑定到本次内存输出流，按字节位置稳定合并诊断，
不从 SQL 或正文猜码；相同位置保持结构化通知原顺序。没有结构化通知的
路径保留原来的单次旧通知扫描。Root 仅接入它已有的活动接收器，未把该
通用诊断草稿并入纯提交，也未改写旧式行数据的解释规则。

另加 24 项新 API 组件断言，覆盖 UTF-8 字节位置、显式绑定而非偶然 stdout、
独立/嵌套接收器、异常恢复、未知/不可定位输出、调用方伪造位置被丢弃、
8 线程位置隔离与原样 CLI 回退。位置只在本次传输内存中存在，不进磁盘
或协议字段；不声称整个项目诊断迁移、任意嵌套 SQL 输出载体均已完成。
